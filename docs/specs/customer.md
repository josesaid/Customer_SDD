# Spec: Customer

Source of truth for the behavior of the customer module.
Any behavior change starts by updating this file.

## Entity

- `id`: Long, generated by the system
- `firstName`: String, required, 2–50 characters
- `lastName`: String, required, 2–50 characters
- `email`: String, required, valid format, max 255, unique (stored in lowercase)
- `phone`: String, optional, format `+?[0-9]{7,15}`
- `active`: boolean, defaults to `true`
- `createdAt`: Instant, generated on creation

## Operations

### CUST-01 Create customer
- `POST /api/customers`
- Body: `firstName`, `lastName`, `email`, `phone` (optional)
- 201 with a `Location` header and the created customer
- 400 if validation fails
- 409 if the email already exists

### CUST-02 Get customer
- `GET /api/customers/{id}`
- 200 with the customer (also when inactive)
- 404 if it does not exist

### CUST-03 List customers
- `GET /api/customers?active=true|false` (optional filter)
- 200 with the list sorted by `lastName`

### CUST-04 Update customer
- `PUT /api/customers/{id}` (full replacement of the editable fields)
- 200 with the updated customer
- 400 if validation fails
- 404 if it does not exist
- 409 if the email belongs to another customer

### CUST-05 Logical delete
- `DELETE /api/customers/{id}`
- 204; sets `active = false` and does not remove the record
- 404 if it does not exist
- Deleting an already inactive customer also returns 204 (the operation is idempotent)

## Error format

All error responses use RFC 7807 (`ProblemDetail`).
Field validation errors include an `errors` property with the detail per field.

## Traceability

Each test in `CustomerApiTest` includes the ID of the operation it verifies (`CUST-0X`) in its `@DisplayName`.
If an operation is added to this spec, it must have at least one test with its ID.
